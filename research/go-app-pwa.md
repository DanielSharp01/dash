# go-app for Dash's capture PWA

Research note, 4 October 2026. Sources are the [go-app repository](https://github.com/maxence-charriere/go-app), its [current getting started guide](https://go-app.dev/start.html), [Go's WebAssembly guide](https://go.dev/wiki/WebAssembly), and browser API documentation. This is a code and documentation review, not a device test.

## How it works

go-app is a Go UI library. Components implement `Render() app.UI` and construct HTML with calls such as `app.Div()`, `app.Input()`, and event handlers. Routes are registered with `app.Route`. The getting started path builds the same Go program twice: `GOOS=js GOARCH=wasm go build -o web/app.wasm` produces the browser program, while a normal `go build` produces an HTTP server. The server uses `app.Handler` to serve the page, Wasm, support scripts, manifest, and other assets. It [pre-renders the initial HTML](https://raw.githubusercontent.com/maxence-charriere/go-app/master/pkg/app/http.go) on the server; the Go Wasm program then runs browser interactions. The [README's example](https://github.com/maxence-charriere/go-app#declarative-syntax) and [getting started guide](https://go-app.dev/start.html) show the component, routing, and two-build arrangement. Go-app also provides [static website generation](https://raw.githubusercontent.com/maxence-charriere/go-app/master/pkg/app/static.go), so its UI choice does not require Dash to keep a Go backend. Go's [Wasm guide](https://go.dev/wiki/WebAssembly#javascript-goosjs-port) explains the runtime's `wasm_exec.js` support file and says it must match the compiled program's major Go version.

go-app offers access to JavaScript values through `app.Value`, `app.Window()`, and `app.FuncOf`, backed by Go's `syscall/js`. Its [`Value` interface](https://github.com/maxence-charriere/go-app/blob/master/pkg/app/js.go) includes property access, method calls, constructors, and Promise `Then`. That is the route to browser APIs and JavaScript scanning packages; writing the UI in Go does not eliminate JavaScript interoperability work. The same source warns that blocking a Go callback invoked by JavaScript blocks the event loop. Go [labels `syscall/js` experimental](https://pkg.go.dev/syscall/js).

The repository currently advertises the `/v11` Go module and Go 1.18 or newer in its [README](https://github.com/maxence-charriere/go-app#install), and its [releases page](https://github.com/maxence-charriere/go-app/releases) lists v11. Older wiki pages and examples refer to v8 or v9, so implementation details from those pages should be checked against v11 source before adopting them.

## PWA and offline capture

go-app supplies a manifest and service worker. Its [published worker](https://raw.githubusercontent.com/maxence-charriere/go-app/master/docs/app-worker.js) precaches listed resources, including `app.wasm`, `wasm_exec.js`, scripts, styles, and `/`; its fetch handler returns a cached response when present, then falls back to the network. The project's [HTTP Handler documentation](https://github.com/maxence-charriere/go-app/wiki/HTTP-Handler) describes versioned worker updates and offline app resources, although that wiki page is old. This can keep the UI launchable after a successful online visit. It does **not**, by itself, save a new food capture, persist an offline outbox, or maintain a searchable item catalogue. The published worker does not add responses fetched later to its cache. [MDN distinguishes HTTP response caching from IndexedDB structured data storage](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Reference).

For Dash, an offline barcode scan should produce a local record such as code, optional name, amount, time, and an unresolved-item state before any network request. Cached items can be searched when present; an unknown code remains an unresolved capture until lookup succeeds. Use browser storage such as [IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API) for captures, an outbox, and the chosen subset of item data, then define sync and conflict behavior. Go-app does not provide that product workflow. A service worker can cache app files, while the client data store holds records. This is an architectural inference from go-app's worker and the browser storage APIs.

## Camera and product barcodes

A go-app page can call `navigator.mediaDevices.getUserMedia()` through its JavaScript bridge, attach the stream to a video element, and pass frames to a decoder. The browser requires a secure context, ordinarily HTTPS or localhost, and user permission. Permission denial, missing cameras, and unavailable constraints need a manual-code or name-entry fallback. [MDN's `getUserMedia` reference](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia) documents these requirements; [go-app's JS bridge](https://github.com/maxence-charriere/go-app/blob/master/pkg/app/js.go) provides the interop mechanism. The camera can operate while the backend is down once the app shell is loaded; that conclusion follows from the browser API being local, not a documented go-app feature.

The browser's native [`BarcodeDetector`](https://developer.mozilla.org/en-US/docs/Web/API/BarcodeDetector) can recognize linear formats such as EAN-13, but MDN marks it as limited availability and experimental. Check `BarcodeDetector` and `getSupportedFormats()` at runtime. A separate browser-side decoder or manual entry is needed for devices without it. A photo/file input may also be a useful fallback, but its behavior needs device testing. go-app does not appear to offer a barcode component in its public getting-started docs; the scanner would be Dash code or an integrated JS package.

## Fit against React for this prototype

go-app **can support** an installable PWA with offline quick capture and camera scanning. It does not give Dash's hard requirements for free: local records, catalogue selection, sync, scanner fallback, and permission handling are application work in either stack. With go-app, browser integration crosses the Go/JavaScript bridge; with React, those browser APIs and common barcode packages can be called directly from TypeScript. That is a development-cost inference from go-app's [`Value`/`FuncOf` bridge](https://github.com/maxence-charriere/go-app/blob/master/pkg/app/js.go) and the browser API documentation, not a measured performance comparison.

For the immediate capture prototype, React is the simpler choice if fast UI iteration and Agentation are the priorities. go-app is a reasonable option if writing the client in Go matters enough to accept the extra browser interop and a two-target Go build. The fact that it uses Wasm does not prevent camera use or offline operation. Its practical cost here is that Dash's most important interactions are browser APIs and local persistence, which still need explicit design and code.

Before a production decision, measure startup/download size and scan responsiveness on the actual target phones. No figures are asserted here because this review did not build either app. Also verify camera and scanner behavior in the intended browsers; native barcode detection is not uniformly available.

The site's older [getting started page](https://go-app.dev/getting-started) currently stops at “Loading getting-started.md...” in the fetched page, while the newer [start guide](https://go-app.dev/start.html) contains the actual instructions. This partly explains the documentation friction, but it does not affect the library's technical feasibility.
